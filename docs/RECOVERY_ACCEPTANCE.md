# 故障恢复验收（进行中）

目标：20–30 名师傅同时使用时，保存的任务可恢复；单单异常隔离；不因重试造成重复业务写入。不能将此目标解释为外部服务永不故障。

## 第一批：同步任务安全恢复

覆盖 outbox 节点：签收、检测完成、维修完成、寄回、工单完成。

- 明确提交前的暂时性错误：有限次数重试，超限进入人工处理。
- 已标记结果未知的错误：隔离并要求核对，禁止自动和手动盲目重放。
- 重启后遗留的执行中任务：隔离为结果未知，不直接再次提交。
- 调度器抛出异常：释放调度占位，使后续扫描可重新安排。
- 前端显示结果未知提示，并隐藏不安全的重试入口。

验证命令：`node --test test/recovery-fault-injection.test.js test/recloud-sync-outbox.test.js`。
测试仅使用临时存储及模拟适配器；60 个独立任务中一单异常、其余完成的测试，不代表真实 60 用户容量，也不代表共享瑞云浏览器通道已完成隔离验收。

## 上线前仍须完成

第二批进展（尚未完成整批）：维修提交前保存 SUBMITTING 断点，提交调用及提交后保存失败标记结果未知。outbox 保存适配器返回的本地收尾所需结果；本地回调或终态写入失败时，仅重试本地收尾；带结果断点的执行中任务在重启后走本地恢复。结果断点本身保存失败仍要求核对瑞云，不得盲目重放。模拟测试覆盖这些边界，不代表所有真实适配器已经完成审计。

已接入维修完工的保守自动核对：仅在 SUBMITTING/SUCCESS 断点指纹匹配且远端读回确认最终提交完成时，转为本地收尾。未确认或读取失败继续隔离；不自动推断“未执行”并重试。后台一次只调度一个核对任务，每单核对间隔至少五分钟，不等待核对结束再调度普通任务。共享浏览器通道本身的阻塞隔离仍需独立验收。其他节点尚未接入该自动核对执行器。

通道恢复补充：业务超时现在覆盖页面打开；关闭页面不再阻塞超时返回；超时后才打开的页面不会执行原业务操作。`test/recloud-session.test.js` 使用模拟连接覆盖打开/关闭卡住及执行位置替换。实际浏览器进程资源回收、持续超时后的资源占用、共享登录页与业务页隔离，仍需真实隔离环境验证。

1. 逐一核查所有真实写入适配器：提交后超时必须标记结果未知，不能被误归类为普通网络错误。
2. 按业务节点实现瑞云结果只读核对；确认已成功则补齐本地状态，确认未执行才允许重试。目前只有满足断点条件的维修完工接入自动核对，其他未知结果仍需核对，不是完整自动恢复。
3. 核验不经过 outbox 的签收、检测、建维修单等直接流程；不能用 outbox 测试替代这些路径的验证。
4. 在隔离环境模拟进程强杀、断网、登录失效、限流、磁盘写入失败、附件中断；检查恢复点及防重。
5. 验证共享浏览器通道卡住时的隔离和重新建立连接，保证不会无限占住其他订单。
6. 使用至少 30 个并发用户及富余负载，混合查询、保存、附件上传和提交；记录响应时间、排队时间、成功率、内存及磁盘变化。
7. 落实负责人异常提醒、人工处理入口、备份恢复和生产服务进程守护。

所有故障注入与负载测试默认禁止写入真实瑞云工单。生产启用和真实业务恢复须单独核对权限及范围。

## 本轮集中交付

- 检测提交前持久化提交意图；外层超时读取最终确认阶段；迟到的确认回调不会继续提交。存在未确认提交意图的检测不自动重放，重启后仍保留保护。明确校验错误后的提交意图也保守保留，需要核对后重置。
- 上传结果未知及上传后附件核验失败具有不可自动重试标记；签收附件和项目核对未知状态不再被巡检直接重试。
- 签收、检测、建维修单的异步调度及延时重试捕获未处理异常，日志不输出异常内容；建单快速重试限制四次，后续依赖巡检及人工处理。
- 同一工单的 outbox 写入串行，不同工单仍可并发。此锁限于一个后端进程，不能宣称跨进程或所有直接流程已经互斥。
- 反复超时后执行位置登记表保持固定大小；并不证明浏览器内存或远端请求一定全部停止。
- 本地已完工但瑞云未成功的异常仍显示，未知结果不再提示正在自动重试。
- 维修核对指纹覆盖完整提交内容。旧版指纹不自动升级为成功依据，历史任务可能需要人工核对。

隔离回归范围：`recloud-session`、`recloud-command-executor`、`recovery-fault-injection`、`recloud-sync-outbox`、`recloud-repair-completion-orchestrator`、`recloud-repair-attachment-uploader`、`recloud-recovery-policy`、`safe-background-retry`、`detection-crash-recovery`、`global-sync-alert`、`database-backup-integrity`、`rate-limit-concurrency`、`business-rate-limit`，均为 `test/*.test.js` 下的对应文件。

已验证：临时子进程 SIGKILL 后检测提交意图仍保留；一个本地回调失败不重放远端写入；60 个混合模拟通道任务中一个失败其余完成；60 个模拟账号同 IP 的 2400 个请求通过；临时 JSON 数据可恢复且损坏备份拒绝恢复。HTTP 测试的上传及提交处理器是模拟处理器，4KB 请求不是大视频上传，不代表生产响应时间或真实瑞云吞吐能力。

## 上传入口并发保护

附件入口在 express.json 之前执行准入，默认两路解析/处理，最多排队 60 个请求、等待 30 秒；配置为 UPLOAD_CONCURRENCY（上限4）、UPLOAD_QUEUE_LIMIT（上限120）、UPLOAD_QUEUE_WAIT_MS（上限60秒）。排队请求暂停应用读取；队满或等待超时返回 503 UPLOAD_BUSY、Retry-After: 3 和未接收提示。断开连接及响应结束释放名额。普通查询和操作位置保存不进入此队列。

四项新增测试覆盖60请求名额分配、排队取消、队满/超时、真实HTTP的8个1MiB请求最多两路进入解析且健康查询仍可返回。保护限制并发分配，不保证单个请求内存下降；仍未改流式/分片，仍须独立服务端真实大文件持续压力验证。反向代理缓冲和跨进程总资源限制另行设计；浏览器收到繁忙提示后当前需要用户重试，不宣称已自动续传。

## 上传繁忙的客户端恢复

后续补充：四类附件接口只在 HTTP 503 且 code=UPLOAD_BUSY（明确未接收）时自动重试，最多追加三次，遵循3–30秒等待并增加随机错峰。网络中断、响应异常、结果未知及认证失败不自动重传；同一页面登录代次变化后停止待执行重试。持续繁忙最终提示手动重新上传。此前“繁忙必须手动重试”的限制由这一有限重试替代，不是断点续传。

维修完工页每上传成功一份即加入当前页面附件列表，后续文件失败不再丢掉本批成功项；相同附件ID不重复显示。签收照片改逐张处理，避免同时构造多份Base64。成功项仍须保存草稿或提交才能与完工单持久关联，不保证关闭页面后恢复所有未保存选择。
